## 一、现状盘点

### 1.1 技术栈与部署形态

| 组件 | 技术 | 说明 |
|---|---|---|
| 主程序 `Argus.exe` | .NET 8 WinForms（net8.0-windows） | 产线每台 FCT 机台一台，Windows 桌面常驻 |
| 本地库 `data/{station}.db` | SQLite（Microsoft.Data.Sqlite 8.0.29 + SQLitePCLRaw 2.1.12，内嵌 SQLite 3.53.3） | WAL 模式，busy_timeout=5000 |
| 聚合副本库 `data/mesh_agg.db` | 同上 | v3.5.0 起每节点存全产线 FAIL 摘要 |
| 独立工具 `FCT-Distributor.exe` | .NET 8 WinForms，零第三方依赖 | 工程/测试用造数与投递，不装产线 |
| Web 看板 | HttpListener（http.sys）+ 内嵌 HTML/JS | 单端口 8081 同时承载推送入口与看板 |
| 外部依赖 | 飞书群机器人 webhook（https） | FAIL 告警 / 离线告警 / 定时汇总 |
| 自检 | 主程序 selftest 约 591 项断言；分发器 selftest 71 项 | 无 CI，靠手动 `dotnet build` + 自检 |

### 1.4 并发与一致性现状（代码事实）

- **WebAggServer**：单 accept 线程 + 每请求 `Task.Run` + `SemaphoreSlim(64,64)` 并发闸，超限立即 503 —— 并发模型健康。
- **MeshPusher**：事件只入内存队列（MaxQueue=5000），后台 watchdog 线程发送，失败进断线补偿，`(machine,seq)` 幂等兜底；队列/水位落盘 `mesh_queue.json`/`mesh_state.json`，重启续推 —— 链路可靠。
- **AggDatabase**：**单 `SqliteConnection` + 全局 `_sync` 锁**，所有操作（InsertFail / FailCount / 分页 / 对账 MAX(seq)）串行执行 —— 当前最核心的扩展性瓶颈。
- **Database（机台本地）**：每次操作 `new SqliteConnection + Open + PRAGMA`（短连接），`BatchInsert` 单事务批量插入，但循环内**每行额外 `SELECT last_insert_rowid()`**。
- **一致性**：同源同 seq 幂等；待办冲突用"认领抢占 + 版本号 last-write-wins"；跨节点全量副本靠 Gossiper 兜底 —— 数据最终一致，够用。

## 二、瓶颈与问题清单（按严重度排序）

| # | 位置 | 问题 | 影响 |
|---|---|---|---|
| B1 | `AggDatabase` | 单连接 + 全局锁，读写全串行 | 节点数/推送频率上来后，插入、查询、对账互相阻塞；看板查询会拖慢入库 |
| B2 | `AggDatabase.InsertFail` | 逐条 INSERT 独立提交，无批量事务 | 高吞吐时 WAL fsync 压力大，放大 B1 |
| B3 | 看板查询 | `FailCount` 用 `COUNT(*)`、分页 `LIKE %kw%` 全表扫（无索引） | 数据量增长后看板变慢；`idx_agg_records_machine` 只覆盖 machine 单列 |
| B4 | `Database.BatchInsert` | 循环内每行一条 `last_insert_rowid()` 子查询 | 历史扫描大批量入库时命令对象/往返开销放大（可用 SQLite 3.35+ 的 `RETURNING` 消除） |
| B5 | `Database.Open()` | 每操作新建连接 | 实时事件 Task.Run 并发多时连接抖动；可复用长连接 + 连接池 |
| B6 | `AppState.CountDiskXml` | `Directory.EnumerateFiles(..., AllDirectories).Count()` 全盘递归 | 统计刷新/看板数据量大时阻塞；建议改为按日期目录增量计数缓存 |
| B7 | 无指标/健康观测 | 只有本地日志 `logs/app.log` | 无法集中观测各节点吞吐、积压、失败率；排障靠人肉看日志 |
| B8 | 无自动备份 | 仅迁移前备份（`BackupDbFile`，当日一次） | 机台本地库/副本库损坏后无恢复点 |
| B9 | XML 按需拉取 | 报告不冗余存储，源机离线时看板无法打开报告 | 容灾缺口（Gossiper 只对账 FAIL 摘要，不对账 XML） |
| B10 | WinForms 形态 | GUI 常驻 = 依赖登录会话、无服务自愈、UI 线程与业务耦合 | 断电/崩溃/会话锁定时可能静默中断（虽有 `agg --install` 自启） |
| B11 | 多 peer 推送串行 | `MeshPusher` 单 worker 顺序向所有 peer 发送 | peer 数增长（>10）后单 peer 慢拖累全链路（有断线补偿兜底，属中风险） |
| B12 | 无对外 API | 数据只在本节点 `mesh_agg.db` + 浏览器看板 | MES/上层系统接入需新开发；多产线联邦无基础 |
| B13 | 数据无限增长 | 无归档/清理策略（`todo_scan_days` 只影响待办登记，不动原始记录） | 长期运行后 db 体积与查询退化 |
| B14 | 配置安全 | token 明文存 config.json；http 明文通道仅警告 | 中风险（内网环境可接受，但应可升级 https） |

> 其余良好项（不必动）：HttpListener 并发闸与 Task.Run 模型、Mesh 幂等与断线补偿、Gossiper 增量对账、解析责任链可配置化、WAL 模式、迁移前备份、去中心化天然无单点。

## 三、目标架构（扩容后形态）

```
┌─ 采集层（每机台，轻量）──────────────────────────────┐
│  FCT 软件 XML ─► Argus.exe（无头模式）                 │
│    ├ 本地 SQLite（热数据，仅本机，可裁剪）              │
│    ├ 解析责任链（Parsing，可配 parsers.json）          │
│    └ 出站推送队列（批量 + 背压 + 幂等）                │
└──────────────┬───────────────────────────────────────┘
               │ HTTP(S) POST 批量事件 / 心跳
┌──────────────▼───────────────────────────────────────┐
│  聚合/联邦层（可 1 台起，随产线扩展）                   │
│    ├ API 网关（鉴权/限流/路由，HttpListener→Kestrel）   │
│    ├ 接收 → 批量入库（事务合并 + 写放大抑制）           │
│    ├ 副本库（SQLite→可选 PostgreSQL 读写分离）          │
│    ├ 对账 Gossiper（间隔自适应 + XML 对账）             │
│    └ 事件总线（内存→可选 RabbitMQ/NATS，跨产线联邦）    │
└──────────────┬───────────────────────────────────────┘
               │
┌──────────────▼───────────────────────────────────────┐
│  消费/展示层                                           │
│    ├ Web 看板（分页 seek / 统计缓存 / 导出异步化）      │
│    ├ 告警中心（飞书，防抖 + 级别路由）                  │
│    ├ 待办/维修（跨机池，LWW 冲突裁决）                  │
│    └ 对外 API（MES 接口，按 SN/机台/时间段查询）        │
└───────────────────────────────────────────────────────┘
┌─ 横切面 ──────────────────────────────────────────────┐
│  可观测：/api/metrics（吞吐/积压/失败/延迟）+ 日志滚动  │
│  容灾：每日备份 + 异地副本 + XML 缓存落盘兜底           │
│  运维：无头服务化（Windows Service）+ 集中状态上报      │
└───────────────────────────────────────────────────────┘
```

**扩容主轴的判断依据**：当前系统 7~10 节点规模下，真正的性能上限不在网络/解析，而在**副本库的串行写**（B1/B2）与**全表扫描查询**（B3）。因此 P0 全部围绕数据库层做低风险手术；P1 补齐可观测与容灾；P2 再做服务形态与 API 化；P3 才是引入消息队列/PostgreSQL 等重件。

## 四、优化方案（按优先级，含落地动作与对应代码位置）

### P0 — 数据库层手术（1 周内，低风险高收益）

#### P0-1 副本库 `AggDatabase` 去全局锁：读写分离 + 长连接池
- **现状**：`AggDatabase.cs` 用 `_sync` 锁 + 单 `_conn`，写、读、对账全串行。
- **动作**：
  1. 写路径：保留一个**写专用连接**（WAL 模式下单写者即可，天然串行但不再被读阻塞），所有 `INSERT OR IGNORE` 走它；`busy_timeout` 保持 5000。
  2. 读路径：新建 `SqliteConnectionStringBuilder { Pooling = true }` 长连接池，`FailCount / LastFailAt / 分页 / MaxSeqPerMachine` 等查询走池内短租，**不再持有全局锁**。
  3. 对账 `MaxSeqPerMachine` 与 Gossiper 拉取读路径，与写并发不再互斥。
- **收益**：看板查询/对账不再阻塞推送入库；多 peer 同时推送的吞吐不再被读拖累。
- **验证**：selftest 新增"写线程 + 读线程并发压测"断言（如 5 写线程 × 1000 条 + 3 读线程 COUNT，全程无 SQLITE_BUSY）。

#### P0-2 批量入库：`InsertFail` 支持事务合并
- **现状**：`HandleFail` 每条独立 `InsertFail` → 每次一个事务。
- **动作**：`MeshReceiver` 改为 50ms 或 100 条聚合一次 `AggDatabase.InsertBatch(List<AggFailRow>)`（单事务），批量参数化，批量后一次性取 `last_insert_rowid()` 序列回填 Id。
- **收益**：WAL fsync 次数降为原来的 1/100，推送高峰吞吐大幅提升。
- **注意**：`(machine,seq)` 幂等不受影响（INSERT OR IGNORE 语义不变）。

#### P0-3 查询索引与分页改造（看板）
- **现状**：`agg_records` 索引：`idx_agg_records_ingest(ingest_ts)`、`idx_agg_records_machine(machine)`；分页用 `LIKE %kw%` + `COUNT(*)`。
- **动作**：
  1. 新增复合索引：`(machine, id)`、`(test_date, id)`、`(ingest_ts DESC)`；有 `LIKE` 搜索的列（sn/model/fail_reason）评估 FTS5，量大时再上。
  2. 分页从 `OFFSET` 改为 **keyset（seek）分页**：`WHERE id < @lastId ORDER BY id DESC LIMIT n`，前端带上一页末条 id。大页深翻页不再全表扫。
  3. `COUNT(*)` 改为两档：页首总数用 `COUNT(*)`（可缓存 5s），列表本身走 seek。
- **验证**：selftest 加"1 万行数据分页查询耗时断言"；看板人工验证翻页无感。

#### P0-4 机台本地库 `Database`：连接复用 + `RETURNING` 消除逐行取 id
- **现状**：`BatchInsert` 循环内每行 `SELECT last_insert_rowid()`（见 `Database.cs:328-336`）。
- **动作**：
  1. SQLite 3.53.3 支持 `INSERT ... RETURNING id`，把"插入 + 取 id"合并为一条语句，去掉循环内子查询与命令对象反复创建。
  2. `Database` 改为持有**常驻写连接**（`Open()` 改为惰性建一次长连接），实时事件并发不再反复 Open/Close。
  3. 保留 WAL + busy_timeout，历史扫描大事务继续走单事务。
- **收益**：历史扫描（首日几十万文件）入库时间显著下降；实时路径连接抖动消除。

#### P0-5 WAL checkpoint 与 VACUUM 运维策略
- **动作**：每日低峰（如 03:00）执行 `PRAGMA wal_checkpoint(TRUNCATE)` + 尺寸超阈值（如 >512MB）时 `VACUUM`；把策略做成 `config.json` 可配项（`db_maintenance_hour`）。
- **注意**：`VACUUM` 前必须 `Checkpoint` 并确认无活跃读事务（可先 `ClearAllPools`）。

### P1 — 可观测与容灾（2 周内）

#### P1-1 指标埋点 + `/api/metrics`
- 在 `AggDatabase`（写吞吐/写延迟/排队）、`MeshPusher`（队列积压/丢弃数/逐 peer 失败率）、`WebAggServer`（请求数/延迟/503 数）、`MeshReceiver`（接收数/幂等忽略数）加计数器（`Interlocked` 即可）。
- 暴露轻量 JSON `/api/metrics`（或 Prometheus text 格式，二选一，无需引依赖），供脚本/看板拉取。
- 好处：Gossiper 对账补缺数、队列溢出（`OverflowNotifyMinMs` 已有）都能量化观察。

#### P1-2 自动备份与恢复点
- 扩展 `Database.BackupDbFile`（现在仅迁移前调用）为**每日定时备份**：WAL checkpoint → 复制 `{db}.bak-yyyyMMdd`，保留最近 N 份（默认 7）。
- 副本库 `mesh_agg.db` 同样备份；多节点本身是副本冗余，再叠加每节点本地备份，容灾即可闭环。
- 验证：selftest 断言"备份文件可打开且行数一致"。

#### P1-3 XML 报告容灾：对账纳入 XML 缓存
- 现状：`MeshReceiver.FetchXmlForFail` 跨机按需拉取，源机离线即失败。
- 动作：聚合节点把"本机曾成功拉取过的 XML"落盘缓存到 `data/agg_xml/`（按 machine/date 分目录），拉取先查缓存；Gossiper 摘要可附带 `xml_available` 标志，缺口补推时一并补 XML 引用。
- 收益：源机离线时，看板仍能打开历史报告（`WebAggServer` 的 `AggXmlRoot` 白名单已具备落盘能力，改动集中在 MeshReceiver 拉取侧）。

#### P1-4 日志滚动与保留
- `Logger` 当前单文件 `logs/app.log`。增加按大小（如 20MB）滚动 + 保留 7 份（`logs/app.log.1~7`）。
- 为 P2 的服务化打底：启动参数加 `--service` 时日志可切到控制台/事件日志。

### P2 — 服务形态与 API 化（1 个月）

#### P2-1 无头服务化（关键架构动作）
- 现状：GUI 常驻（MainForm/AggCenterForm），Web 模式靠 `Argus.exe agg --web` 无窗体 CLI。
- 动作：
  1. 抽 `HeadlessService`：把 `Engine + MeshNode + WebAggServer + AggAlertService` 组装逻辑从 GUI 解耦（当前 `Program.cs` 已支持 `agg --web` 无窗体，把该路径提升为一等公民）。
  2. 提供 Windows Service 注册（`sc create` / 自研 `--install-service`），`SERVICE_AUTO_START` + `RecoveryOptions`（失败重启 3 次）。
  3. GUI 变薄壳：主程序进程即服务进程；或 `Argus.exe agg --service` 单独部署为服务，GUI 连接本地 127.0.0.1 API 呈现。
- 收益：会话锁定时不中断采集；断电重启自动拉起；为容器化/无人值守铺路。

#### P2-2 看板与 API 增强
- 统一 API 版本化：`/api/v1/...`；新增 MES 常用查询：按 SN 反查、按时间段导出、按机台良率。
- 导出异步化：`/api/export.csv` 大导出改为"创建任务 → 轮询进度 → 下载产物"，避免阻塞 HttpListener worker。
- 统计缓存：主页机台卡片/FAIL 总数改为内存缓存（如 5s TTL），避免每次 `COUNT(*)`。

#### P2-3 MeshPusher 多 peer 并发发送
- 现状：单 worker 顺序推所有 peer（`_http.Send` 同步 5s 超时）。
- 动作：worker 改为逐 peer 并行（`Parallel.ForEach` 或按 peer 各起一个发送协程，仍共享同一队列），单 peer 慢不拖累其他 peer；保留断线补偿与幂等。

#### P2-4 Gossiper 间隔自适应
- `_intervalSec` 从固定 30s 改为：在线稳定期放大（60s），检测到缺口/刚恢复时收紧（10s），降低心跳与对账的网络开销。

### P3 — 规模扩展（按需，不预做）

#### P3-1 数据层分档
- 路径 A（保持 SQLite，最省）：热数据保留本地，`agg_records` 按 `test_date` 月归档表或独立归档库；配合 P0-5 的 checkpoint/VACUUM。
- 路径 B（引入 PostgreSQL，节点数 >30 或需跨产线报表时）：单实例 + 读写分离（只读副本供看板/报表），主库承担写入；用现有 `(machine,seq)` 幂等键直接平移，改动集中在 `AggDatabase` 的 SQL 适配层（建议先抽 `IFailStore` 接口，P0 时一并做，P3 直接实现 PG 版）。

#### P3-2 事件总线（可选）
- 直推 HTTP 在 >50 节点时考虑引入 RabbitMQ/NATS：机台 → 消息 → 聚合订阅。好处是削峰 + 消费独立扩展；代价是引入运维组件。
- 前置条件：先有 P1-1 指标证明"HTTP 直推确实到瓶颈"，再上总线，避免过度设计。

#### P3-3 多产线联邦
- 每产线一个聚合联邦，联邦间只同步"待办 + 汇总指标"，不做全量 FAIL 复制；上层看板按产线过滤。
- 当前 `peers` 静态发现可扩展为"发现服务器/配置下发"，减少新增机台的配置操作。

## 六、风险与权衡

1. **最小侵入原则**：P0/P1 全部保持 SQLite 与现有 `(machine,seq)` 幂等协议不变，机台端 `config.json` 无需改动，覆盖升级即可回滚。
2. **读写分离的边界**：WAL 模式下单写者设计简单可靠；若未来要多写（同一副本库多节点写），再评估"单主库 + 同步"或 PG。现阶段去中心化下每节点自己的副本库由本节点单写，天然适配单写者。
3. **过度设计警告**：≤10 节点、单产线规模下，**不要**上消息队列/PostgreSQL/容器编排——P3 均为条件触发，不预做。
4. **一致性**：最终一致 + 幂等 + Gossiper 对账已满足产线需求；引入总线后要保持同样的"幂等键 + 水位续推"语义，这是任何中间件替换不可逾越的基线。
5. **安全**：P2 服务化后建议强制 https（自签即可）+ token 从注册表/受保护配置读取，消除 config.json 明文 token。

## 七、结论

- **当下最值得做的三件事**：① `AggDatabase` 去全局锁 + 批量入库（P0-1/P0-2）；② 看板查询索引与 seek 分页（P0-3）；③ 机台库 `RETURNING` + 长连接（P0-4）。三者合计约 1 周工作量，可消除当前规模下 80% 的可见性能问题。
- **下一里程碑**：无头服务化（P2-1），把采集能力从 GUI 会话中解放，为无人值守与规模扩展奠基。
- **扩容触发线**：节点 >30 或需要跨产线报表 → 数据库升级 PG；推送吞吐告警（/api/metrics 可观察）→ 引入消息总线。
