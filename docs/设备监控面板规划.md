# 局域网设备信息监控 Dashboard — 功能规划

> 版本：v1（2026-08-27）｜范围：需求分析 + 功能模块 + 数据流 + 架构建议 + 实施拆解
> 背景衔接：《架构优化与扩容方案.md》P0 已落地（v3.5.3）；本规划作为 **Argus 生态的新功能扩展**编写，
> 所有复用点均标注了现有代码位置，便于直接落码。

---

## 1. 需求概述

在局域网内，通过 Web 面板（dashboard）集中**拉取并查看已安装设备的信息**：
- 已安装设备 = 产线上部署了 Argus 的 FCT 机台（后续可扩展任意运行 Agent 的设备）
- 查看内容 = 在线状态、系统信息（CPU / 内存 / 磁盘 / 系统版本 / 运行时长 / 网络等）
- 交付形态 = 在现有 Web 看板上新增「设备」视图，与 FAIL 看板并存

**核心命题**：设备信息从哪来、怎么存、怎么展示、怎么告警、怎么不拖垮现有 FAIL 链路。

---

## 2. 关键决策（含推荐结论）

### D1 系统归属 —— 推荐：扩展 Argus（而非独立新系统）

| 维度 | 方案 A：Argus 内扩展（推荐） | 方案 B：独立新系统 |
|---|---|---|
| 采集通道 | 复用 mesh 心跳/推送通道（30s 已存在） | 需新写 Agent + Server + 前端 |
| 存储 | 复用 `AggDatabase`（新增 2 张表） | 新建数据库与运维 |
| 看板 | 复用 `WebAggServer` 内嵌 HTML（新增页签） | 全新建站 |
| 鉴权 | 复用 `agg_token`（header/cookie/固定时间比较） | 重新设计 |
| 告警 | 复用 `AggAlertService` 飞书通道 | 重新设计 |
| 发布 | 复用 `make_release.ps1` update 包覆盖升级 | 独立发布链路 |
| 新增成本 | 心跳扩展 + 2 表 + 3 API + 1 页 + 自检 | 全套 |

**结论**：先做 A——产线机台已常驻 Argus.exe，这是"已安装设备"最自然的定义；B 的 Agent 侧在 Phase 4 通用化（.NET 跨平台可支持 Linux），Server 侧届时复用同一套 API。

### D2 采集机制 —— 推荐：设备端被动上报（顺带扩展心跳）

| 机制 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| 主动轮询（面板定期请求设备） | 实现直观 | ①N 浏览器 × M 设备 = 查询放大；②设备离线时无法区分「设备挂了」与「面板网络故障」；③需要面板掌握每台设备可达地址 | 设备少且要求被动展示 |
| **被动上报（设备端定时推送，推荐）** | ①离线判定天然可靠（心跳超时）；②mesh 断线补偿/幂等续推机制直接可用；③聚合端单写者，契合 `AggDatabase` 读写分离模型；④面板只读缓存，查询成本恒定 | 需要设备端装 Agent（Argus 已满足） | 本项目 |

**结论**：被动上报。具体分两级：
- **心跳携带轻量状态**（30s，复用 `/api/mesh/heartbeat`）：`cpu_usage`、`mem_usage` 两个数——心跳本身就要发，顺带捎上，零额外连接
- **详情独立上报**（5min，新端点 `/api/mesh/info`）：L1 全量系统信息（见 §3）

> 系统信息不追求强一致：上报失败下周期自动补齐，**不走** `mesh_queue.json` 断线补偿队列（那是 FAIL 事件的强一致通道，别拿大 payload 去污染它）。

### D3 设备发现 —— 推荐：静态 peers 清单 + 可选 mDNS

- 现有 `config.json → peers` 静态邻居清单就是设备列表（聚合端 `MeshReceiver.GetPeerStatuses()` 已维护在线视图）——产线设备固定，静态配置可控、无广播噪音
- 自动发现（IP 段扫描 / mDNS）列为 Phase 4 可选增强：适合临时接入的工程笔记本等非固定设备

## 3. 设备信息维度（三级）

| 级别 | 内容 | 来源 | 周期 |
|---|---|---|---|
| **L0 在线状态**（已有） | machine、online、last_seen、queued、last_seq | 现有心跳 | 30s |
| **L1 基础系统信息**（本次新增） | hostname、os、os_version、ip、mac、cpu_model、cpu_cores、cpu_usage、mem_total_mb、mem_used_mb、disk_total_gb、disk_free_gb、uptime_sec、argus_version | 新 `DeviceInfoCollector` | 5min |
| **L2 进阶**（可选，Phase 3+） | 网卡流量、磁盘 IO、进程数、温度、GPU、历史趋势采样 | 同上扩展 | 按需 |

采集实现零第三方依赖：`Environment`（OS/版本/运行时长）、`DriveInfo`（磁盘）、`PerformanceCounter` 或 `Process` 采样（CPU/内存）、`Dns.GetHostEntry`（IP）。WMI 可用时补充 cpu_model / mac，不可用时降级为 `Environment.MachineName` + 空值（看板显示「未采集」），不影响 L0/L1 主路径。

## 4. 功能模块划分

```
┌─ 采集端（机台 Argus.exe 内新增）─────────────────────┐
│  DeviceInfoCollector（新）                             │
│    ├ L1 采集（5min 定时，零依赖）                      │
│    └ 心跳轻量状态注入（30s，扩展 MeshPusher 心跳 JSON）│
└──────────────────────┬──────────────────────────────┘
                       │ POST /api/mesh/heartbeat(+system) / /api/mesh/info
┌──────────────────────▼──────────────────────────────┐
│  聚合端（WebAggServer / AggDatabase 扩展）            │
│    ├ device_info 表（machine PK 快照，upsert）        │
│    ├ device_samples 表（历史采样，按天滚动保留）       │
│    ├ GET /api/devices                 （总览，5s 缓存）│
│    ├ GET /api/devices/{machine}       （详情）        │
│    └ GET /api/devices/{machine}/samples（趋势序列）   │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────┐
│  展示层（看板新增「设备」页签，沿用黑白红主题）         │
│    ├ 设备总览卡片网格（状态灯 + CPU/内存/磁盘迷你条）   │
│    ├ 单设备详情页（L1 全量 + 3s 自动刷新）             │
│    └ 历史趋势（CPU/内存/磁盘折线，canvas 自绘）        │
│  告警：AggAlertService 定时扫描 device_info           │
│    └ 磁盘 <10% / CPU >90% 持续 N 分钟 / 离线 >阈值 → 飞书│
└────────────────────────────────────────────────────┘
```

### 4.1 采集端
- **DeviceInfoCollector.cs**（新）：`Start()` 后按 `device_info_interval_sec`（默认 300）采集 L1，经 `MeshPusher` 的 HTTP 通道 POST 到所有 peer 的 `/api/mesh/info`（带 `X-Agg-Token`）
- **MeshPusher.BuildHeartbeatJson()**（改）：心跳对象追加 `system:{cpu_usage, mem_usage}` 两个轻量字段——对端心跳解析器向后兼容（缺字段视为未知）

### 4.2 聚合端
- **AggDatabase**（改）：新增 `Open()` 内建表
  ```sql
  CREATE TABLE IF NOT EXISTS device_info (
    machine TEXT PRIMARY KEY,
    hostname TEXT, os TEXT, os_version TEXT, ip TEXT, mac TEXT,
    cpu_model TEXT, cpu_cores INTEGER, cpu_usage REAL,
    mem_total_mb INTEGER, mem_used_mb INTEGER,
    disk_total_gb REAL, disk_free_gb REAL,
    uptime_sec INTEGER, argus_version TEXT,
    last_seen TEXT, updated_at TEXT
  );
  CREATE TABLE IF NOT EXISTS device_samples (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    machine TEXT NOT NULL, ts TEXT NOT NULL,
    cpu_usage REAL, mem_used_mb INTEGER, disk_free_gb REAL
  );
  CREATE INDEX IF NOT EXISTS idx_samples_machine_ts ON device_samples(machine, ts);
  ```
- **MeshReceiver**（改）：`HandleInfo(json)` 解析后 `upsert device_info` + 写入一条 `device_samples`（每 5min 一条，30 台 × 288 条/天 = 8640 行/天，SQLite 无压力）
- **WebAggServer**（改）：新增三个 GET 路由，全部过现有 `agg_token` 鉴权；`/api/devices` 用 5s 缓存（复用 `FailCountCached` 的同款模式），避免每浏览器轮询都全表扫

### 4.3 展示层
- 看板 HTML 新增「设备」页签（内嵌 const 字符串追加，沿用现有 `3s 轮询` 刷新节奏）
- 卡片语义沿用黑白红体系：在线 = 墨黑、离线/超阈值 = 主红、未采集 = 中性灰
- 趋势图用 **canvas 自绘轻量折线**（延续零外部资源原则，不引 Chart.js——离线可用、无 CDN 依赖）

### 4.4 配置（config.json 新项，全部带缺省、向后兼容）
```jsonc
"device_info_enabled": true,        // 机台端是否采集上报（默认 true）
"device_info_interval_sec": 300,    // L1 详情上报周期
"device_samples_retain_days": 7,    // 聚合端 samples 保留天数（DbMaintenance 顺手清理）
"device_alert_disk_free_gb": 10,    // 磁盘剩余 < 该值告警（0=关闭）
"device_alert_cpu_pct": 90          // CPU 持续 > 该值告警（0=关闭）
```

## 5. 数据流设计

```
机台 DeviceInfoCollector
  ├ 30s ── 心跳(含 system:{cpu,mem}) ──► /api/mesh/heartbeat ──► HandleHeartbeat（更新在线视图）
  └ 5min ─ L1 详情 ──► /api/mesh/info ──► HandleInfo ──► AggDatabase
                                                          ├ upsert device_info（快照）
                                                          └ insert device_samples（趋势）
看板轮询（3s）
  └ GET /api/devices ──► FailCountCached 同款 5s 缓存 ──► 返回总览 JSON
AggAlertService 扫描（1min）
  └ device_info 判定磁盘/CPU/离线阈值 ──► 飞书卡片（沿用现有防抖）
```

关键约束（对齐现有架构）：
- **单写者**：所有 device_* 写入走 `AggDatabase` 写锁（与 FAIL 入库同一把锁，WAL 下单写者天然串行），读走短租读连接——不引入新并发模型
- **不污染 FAIL 通道**：系统信息不上 mesh 断线补偿队列、不参与 `(machine,seq)` 幂等；丢了下轮补
- **缓存降级**：设备从未上报时 `/api/devices` 仍返回该机台条目（来自 peers 在线视图），字段置空并标「未采集」

## 6. 技术方案与选型

| 项 | 选型 | 理由 |
|---|---|---|
| 后端 | 延续 .NET 8 + HttpListener | 零新组件；≤30 台规模无压力 |
| 存储 | SQLite（device_info + device_samples 两表） | 采样量 ~8.6k 行/天，远低于时序库门槛 |
| 采集 | .NET 内置 API（Environment/DriveInfo/Process/WMI 可选） | 零第三方依赖，与项目基调一致 |
| 通信 | HTTP/REST（复用 mesh 通道） | 3s 级刷新用 HTTP 足够；WebSocket 留给 Phase 4 大屏 |
| 前端 | 内嵌单文件 HTML/JS + canvas 自绘折线 | 延续零外部资源、离线可用 |
| 告警 | 复用 AggAlertService + 飞书 | 已有防抖与卡片体系 |
| 保留策略 | device_samples 按天滚动，DbMaintenance 日清理 | 防无限增长（B13 既有原则） |

**明确不上**（过度设计警告，≤30 台）：MQTT/消息队列、时序数据库（InfluxDB/TDengine）、WebSocket 长连接、容器编排。

## 7. 非功能性需求

- **安全**：沿用 `agg_token`（Header/Cookie 双通道 + 固定时间比较）；设备信息接口与 FAIL 看板同一鉴权面；防火墙内网网段规则已有（v3.5.1）。注意：设备信息（IP/MAC/主机名）属内网敏感信息，面板不应在未鉴权时暴露——现有鉴权已覆盖
- **性能**：30 台 × 30s 心跳 = 1 req/s；× 5min info = 0.1 req/s；看板 10 个浏览器 × 3s 轮询 = 3.3 req/s（5s 缓存后命中内存）。总量 <10 req/s，SQLite WAL 无压力
- **兼容性**：Windows 10/11 + .NET 8 Desktop Runtime（产线已具备）；WMI 不可用时降级；Agent 未来可跨平台（.NET 8 支持 Linux/macOS）
- **可扩展性**：API 形态 `GET /api/devices*` 预留 `?filter=&sort=`；跨产线联邦沿用 peers 对账（Phase 4）

## 8. 实施步骤拆解

| 阶段 | 内容 | 预估 | 验收标准 | 版本线 |
|---|---|---|---|---|
| **P1 设备总览** | 心跳扩展 + DeviceInfoCollector + device_info 表 + /api/devices + 看板设备页签 | 2~3 天 | 30 台机台在线/离线/CPU/内存/磁盘呈现在面板；离线 90s 内标红；自检 +N 项全绿 | v3.6.0 |
| **P2 详情与趋势** | device_samples + 详情页 + canvas 趋势图 + 采样保留清理 | 2~3 天 | 单机详情 L1 全量可见；趋势图随 3s 刷新；7 天数据自动清理 | v3.6.x |
| **P3 告警** | 磁盘/CPU/离线规则 + 飞书卡片 + 导出 CSV | 2~3 天 | 构造超阈值场景触发飞书告警（防抖生效）；导出含全量字段 | v3.7.0 |
| **P4 扩展（按需）** | mDNS 自动发现 / Linux Agent / WebSocket 大屏 | 按需 | 非固定设备可发现；跨平台采集 | 条件触发 |

**发布衔接**：沿用 `make_release.ps1`（update 包覆盖升级，config.json 缺省向后兼容）；自检工程同步加「P1 设备」断言组（心跳扩展解析、info upsert 幂等、缓存命中、告警阈值双分支）。

## 9. 风险与权衡

| 风险 | 缓解 |
|---|---|
| 心跳 payload 变大拖慢 mesh | 心跳只带 cpu/mem 两个数；全量走 5min info 独立端点 |
| 采集（WMI）5min 一次的开销 | 可忽略；失败降级不阻塞主链路 |
| /api/devices 轮询拖慢 FAIL 查询 | 5s 内存缓存 + 短租读连接（P0 模型已就位） |
| samples 无限增长 | 按天滚动保留（默认 7 天）+ DbMaintenance 清理 |
| 与 FAIL 看板并发带宽 | 设备信息 ~KB 级，量级远小于 XML 拉取 |
| 过度设计 | ≤30 台硬约束不上消息队列/时序库（同方案文档 P3 触发线） |

## 10. 待确认决策清单（开发前需拍板）

1. **系统归属**：扩展 Argus（推荐，D1）还是独立新系统？
2. **设备范围**：仅 FCT 机台（Windows）还是要覆盖 Linux/工作站？（决定 DeviceInfoCollector 是否走跨平台 API）
3. **信息维度**：L0+L1 是否够？L2（网卡流量/磁盘 IO/温度）是否需要？
4. **采样保留**：device_samples 保留天数（默认 7）是否合适？
5. **告警默认值**：磁盘 <10GB / CPU >90% 持续阈值是否合理？是否要加"离线告警"独立开关（现有 agg_fail_alert_minutes 已有离线告警，是否复用）？
