## 2. 修改规范（改代码前必读）

### 2.1 代码风格

- **命名**：公共成员/类型 PascalCase；私有字段 `_camelCase`；局部变量 camelCase；常量大驼峰（如 `PW_RENDERFULLCONTENT`）。
- **注释**：公共 API 写 XML doc（`/// <summary>`）；关键业务逻辑写中文注释说明「为什么」（不只是「做什么」）。
- **文件组织**：一个职责一个文件；`modules/` 下是独立工具箱（自带 namespace）；`Parsing/` 是解析框架。
- **无第三方依赖**：新增功能优先用 .NET 内置库；引入任何 NuGet 包需在文档说明理由并更新 packages.lock.json。

### 2.2 视觉铁律（v3.5.2「Gallery Noir」起）

- **全界面只允许黑、白、红三色**，颜色一律走 `Theme.cs` 令牌（`Theme.Surface` / `Theme.TextMain` / `Theme.Primary` / `Theme.Danger`…），**禁止硬编码色值**。
- 语义映射：正常/在线/完成 = 墨黑；注意/中性 = 灰；失败/离线/待办 = 主红 `#C8102E`。
- 允许「只动颜色与外观」，**不允许动布局**时，必须自检全绿（历史教训：批量替换脚本误伤 4 个源文件，靠逐控件 Bounds 比对自检才拦住）。

### 2.3 Dock 布局铁律（WinForms）

1. **同向 Dock 后 Add 的先停靠**（停靠顺序写反会导致控件重叠/文字悬空——自检有专项断言）。
2. **任何 TableLayoutPanel / FlowLayoutPanel 单元格内的子控件必须显式 `Dock = DockStyle.Fill`**，否则保持默认 200×100 被压扁（v3.8.0 曾因漏设导致整个聚合看板残缺，见 `.workbuddy/memory/2026-08-27.md`）。
3. 内嵌 Form（`TopLevel=false` 进 ToolHost）时**禁用 SplitContainer**（尺寸为 0 会抛异常），分栏用 TableLayoutPanel 的 Absolute + Percent 列宽模拟。
4. 窗口尺寸变化时的自适应逻辑写在 `ClientSizeChanged` 里，不要依赖 `Resize`（内嵌时可能不触发）。

### 2.4 网络与协议铁律

- **原生通道**：机台端 ↔ Web 端只走原生 HTTP/1.1 直连 + JSON，**禁止**第三方中间件 / 代理 / 自定义协议封装 / SMB 文件通道（smb 已 deprecated）。
- **鉴权**：所有写操作与管理接口走 `agg_token`（固定时间比较防时序攻击）；新增敏感路由必须校验。
- **mesh 幂等**：推送事件以 `(machine, seq)` 为幂等键，接收端组提交失败整批回滚 → HTTP 5xx → 对端重推。**新事件类型不得破坏此闭环**。
- **安全基线**：路径穿越防护（`public/` 解析后必须位于 root 内）、CSV 公式注入防护（CWE-1236，导出一律 UTF-8 BOM + `= + - @` 前缀转义）、XML 解析 DTD Prohibit 防 XXE。

### 2.5 数据库铁律

- **AggDatabase 单写者**：写路径走一把写锁 + 常驻 WAL 写连接；读路径用无锁短租连接（读不阻塞写）。
- **禁用 ADO 连接池**：池化句柄长期占用 db 文件会导致备份/清理删不掉文件。
- 批量入库走 `InsertBatch` / 组提交（50ms 或满 100 条一个事务）；维护走 `DbMaintenance`（每日 checkpoint + 阈值 VACUUM）。

### 2.6 前端（public/）规范

- 零第三方库、零外部 CDN（产线离线可用）；CSS 内联 `<head>`、JS 内联 `</body>` 前。
- 浏览器基线：Chrome/Edge/Firefox 90+、Safari/iOS 14+；**不做 IE11**。
- 轮询渲染做数据指纹变更检测（`dataSig()`），数据未变跳过重渲染；尊重 `prefers-reduced-motion`。
- 新增页面 = 一个 `<section data-page>` + 一个 `render*` 函数 + 一个导航按钮，保持模块化。

### 2.7 改动边界（红线）

- **不得破坏已上线接口契约**：端点路径、字段名、幂等键、鉴权方式零变更（要变必须走 API 版本化，如 `/api/v1/...`）。
- 机台端 `config.json` 向后兼容：新增配置项必须带默认值，旧配置缺省可运行。
- 新功能必须同步：①实现代码 ②`selftest` 断言组 ③更新日志.md。三件缺一不可。

## 3. 更新规范（改完怎么收敛）

### 3.1 版本号语义

- 版本号唯一来源：`FctAggregator.csproj` 的 `<Version>`（主程序）；分发器版本号在其独立仓库 `E:\FctDistributor\FctDistributor.csproj`。
- 规则：**X.Y.Z** —— Z = 缺陷修复 / 小优化（如 3.5.3 P0 落地）；Y = 新功能（如 3.8.0 在线 XML 查看）；X = 架构级变更。
- **注意**：发版前必须把版本号提升到位（这是本规范第一条要执行的）。

### 3.2 每次改动的完成清单（Checklist）

1. ✅ 代码改动完成，`dotnet build FctAggregator.csproj -c Release` **0 警告 0 错误**（分发器在其独立仓库单独构建）。
2. ✅ 自检：`dotnet run --project selftest\SelfTest.csproj -c Release` **全量断言通过**（新增功能加断言；新 .cs 文件要手动加进 `selftest\SelfTest.csproj` 的显式 Compile 列表）。
3. ✅ 更新 `FctAggregator\更新日志.md`：**顶部**新增一条，格式见 3.3。
4. ✅ 涉及配置：确认 `Config.cs` 的 Load / Save / known-keys 三处同步。
5. ✅ 涉及 GUI：`Theme.Apply` 覆盖；Dock 顺序与 Fill 检查（§2.3）。
6. ✅ 涉及前端：HTML 改动后复制到运行目录验证（静态服务每次读盘，无需重启）。

### 3.3 更新日志条目模板

```markdown
## YYYY-MM-DD — 一句话主题（vX.Y.Z）

按《xxx.md》第 N 优先级实施完成，兼容性说明（是否改 schema / mesh 协议 / config）。

1. **【编号】标题**：做了什么、为什么、怎么验证。
2. ...

**自检**：新增「xxx」回归组 N 项断言（...），全量 **XXX 项断言通过**。

**明确不做**：...（记录有意放弃的选项，防后人重复踩坑）
```

### 3.4 发布节奏

- 每期功能（或一批 bugfix）完成后走一次完整发布（§4），不要在发布目录里堆积未发版改动。
- 发布前自查：`更新日志.md` 有本次条目、版本号已提升、自检全绿、构建 0 警告。

## 4. 打包规范（发版流程）

### 4.1 一键发布

```powershell
cd E:\Argus-main
.\make_release.ps1                 # 构建 + 打包 + 归档 + 纯净校验 + RELEASE.txt
.\make_release.ps1 -SkipBuild      # 已构建过，只打包归档（省时）
.\make_release.ps1 -Version 3.8.0  # 强制归档版本（默认自动读 csproj <Version>）
```

### 4.2 流程（make_release.ps1 内部 5 步）

1. **构建**：FctAggregator `dotnet build -c Release`。
2. **两个打包器**（各自产出纯净 zip）：
   - `FctAggregator\tools\make_package.ps1` → `Argus-v{ver}.zip`（完整包）+ `Argus-v{ver}-update.zip`（更新包）
   - `FctAggregator\tools\make_package_agg.ps1` → `Argus-Agg-v{ver}.zip`（聚合端纯净包）
   - 分发器包：在其独立仓库 `E:\FctDistributor` 跑 `tools\make_package.ps1` 单独出
3. **归档**：zip 收集到 `Releases\v{ver}\`（幂等，不删历史版本）。
4. **纯净性校验**：每个 zip 解压检查——**不含 `data\` / `logs\` / `*.db` / `*.pdb`**，config.json 为模板（webhook 置空），不污染机台现有数据。
5. **RELEASE.txt**：版本/日期/SHA256/内容说明/纯净声明/部署方式，随版本目录归档。

### 4.3 产物与部署方式

| 产物 | 用途 | 部署方式 |
|---|---|---|
| `Argus-v{ver}-update.zip` | 机台主程序更新 | 解压覆盖（data/logs 不受影响），`tools\deploy_update.ps1` 或手动 |
| `Argus-v{ver}.zip` | 机台完整安装 | 全量解压 |
| `Argus-Agg-v{ver}.zip` | 聚合端后端 | 解压 → `一键部署聚合服务.bat`（或 `Argus.exe agg --install` / `agg --web`） |
| `FCT-Distributor-v{ver}.zip` | 工程造数工具 | 独立仓库 `E:\FctDistributor` 发版，测试/工程人员使用，不装产线 |

## 6. 重要性说明（为什么这些规范与位置重要）

> 以下每条对应上文的「规范」或「文件位置」，说明其对项目存续的实际价值——**产线系统改错一次 = 停线事故**，这些约束是为了把风险挡在提交之前。

### 6.1 修改规范的重要性

1. **§2.2 视觉铁律**：产线现场看板是运维人员的"眼睛"。黑白红三色是用户拍板的品牌级约束（v3.5.2），颜色语义（红=失败/离线）一旦被新代码破坏，运维会**误判设备状态**——这是直接的生产安全风险，不是审美问题。历史教训：批量替换脚本一次误伤 4 个源文件。
2. **§2.3 Dock 布局铁律**：WinForms 布局错误**不报编译错误**，只表现为控件叠压/缺失（v3.8.0 漏设 Dock=Fill 导致整个看板残缺，用户肉眼才发现）。这条铁律 + 自检的 Bounds 比对是防止"改完看不出坏"的关键。
3. **§2.4 网络与协议铁律**：机台间传输是产线数据生命线。引入中间件/代理/新协议 = 增加故障点 + 违背用户明令的"原生通道"架构约束（为此已取消总纲 P3-2 事件总线方向）。幂等键 `(machine,seq)` 一旦破坏，重推会造成**数据重复**，污染良率统计。
4. **§2.5 数据库铁律**：产线机台 7×24 运行，数据库被连接池句柄锁住 → 备份失败 → 数据丢失风险。单写者模型是 P0 优化（v3.5.3）的成果，破坏它等于退回全表串行，高峰期推送会堆积。
5. **§2.7 改动边界**：已上线机台的 config.json 和 API 契约是不能动的"地基"。破坏契约 = 所有已部署机台**集体失效**，且无法热回滚。API 版本化是唯一的合法变更通道。

### 6.2 更新规范的重要性

6. **版本号与更新日志**：产线部署靠 `Releases\v{ver}\` 目录区分版本、靠 RELEASE.txt 的 SHA256 校验完整性。版本号不提升 / 日志不记录，运维就**无法判断机台上跑的是什么版本**，出问题时无法定位、无法回滚（当前 csproj 停在 3.5.3 而代码已到 v3.8.0-demo 就是反面教材）。
7. **自检 647 项 + 0 警告**：这是项目**唯一的自动化质量门**（无 CI）。629→647 项断言覆盖解析口径/幂等/布局/安全，任何改动破坏它们 = 大概率产线回归。新功能不带断言 = 该功能没有验收标准。

### 6.3 打包规范的重要性

8. **纯净性校验**：发布包若混入 `data\` / `logs\` / `*.db`，机台覆盖升级时会**用测试数据污染/覆盖产线真实数据**——这是最高危的事故类型。make_release.ps1 第 4 步的强制校验就是为此存在，任何打包改动不得绕过。
9. **一键发布幂等**：发布流程必须可重复、可追溯（每次归档生成 RELEASE.txt + SHA256）。手工打包容易漏文件/混版本，导致机台行为不一致难排查。

### 6.4 重要文件位置的重要性

10. **`WebAggServer.cs`**：看板与 mesh 的咽喉——新路由、鉴权、限流都在这里加，改错影响所有机台推送与所有浏览器访问。
11. **`Config.cs`**：配置三处同步（Load/Save/known）漏一处 = 配置"保存不生效"或"解析崩"，且不报编译错。
12. **`selftest\SelfTest.csproj` 的显式 Compile 列表**：新 .cs 不加进去 → 自检"看起来全绿"实际没覆盖新代码 → 断言失效假绿（真实踩过：XmlReportHtml.cs 漏加导致断言 0 覆盖）。
13. **`更新日志.md`**：是唯一按时间线记录的"为什么这么做"（含明确不做项），后人改代码前读它可避免重复踩坑、重复造轮子。
14. **`.workbuddy\memory\`**：工作日志记录每次调试的真实根因与验证方法（如 PrintWindow 截图三坑），是项目"活的排障手册"。
