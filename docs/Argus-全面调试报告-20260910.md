### 对原报告的两处自我更正（复核后）

- **Page UiAsync.Debounce 的 Timer "未释放泄漏"**（原 L4）：实测其 `Tick` 内先 `t.Stop()` 再判 `owner.IsDisposed`，窗体销毁后下一拍即自停，**不构成泄漏**。原判断偏严。
- **`UiAsync.Post` 的守卫**（原 L2 涉及的普遍性质疑）：该方法已处理 `IsDisposed`、`IsHandleCreated` 与句柄延迟创建三种情况，**本身是正确写法**；真正漏守卫的只有 `MainForm` 自动更新那处裸 `BeginInvoke`（本轮改为走 `UiAsync.Post`）。
- **"日志缓冲写盘 = 牺牲崩溃可靠性"的推论**（本轮推翻）：该结论只在"缓冲 + 不 flush"时成立。`AutoFlush=true` 的复用式 `StreamWriter` 每行仍立即落盘，省的只是每行的文件 open/close，故 PERF-10 于 v3.40.5 落地。

## 2. 性能问题（Performance）

### PERF-1 🔴 每 1 秒在 UI 线程做注册表 + 串口枚举

**位置**
- `Ui/MainForm.cs:400-412` — 1 秒 `Timer` 的 `Tick()`，第 406 行无条件 `RefreshDeviceOnline()`
- `Ui/MainForm.cs:488-493` — `RefreshDeviceOnline()` → `FctIni.Snapshot(_cfg.FctIniPath)`
- `Core/FctIni.cs:182-213` — `Snapshot()` 每次都调 `ProbePresentComPorts()`（源码注释自述："每次只重探 COM 在线"）
- `Core/FctIni.cs:81-86` → `48-63`（`Registry.LocalMachine.OpenSubKey`）+ `65-78`（`SerialPort.GetPortNames()`）

**问题**：`Tick` 不受当前页面限制（在总览页也跑），每秒一次内核级注册表枚举 + 串口枚举，且**COM 探测结果完全没有缓存**。INI 文本解析本身已按 mtime 缓存（`FctIni.cs:256-283`），**唯独 COM 探测每次重做**。

**复现**：启动 Argus 后停留在任意页面，持续观察；用 Process Monitor 可看到每 1s 一次的注册表读取。机台串口多（现场 FCT.ini 登记了 COM1~COM11 共 11 个）时单次耗时更长。

**影响**：所有页面共有的周期性顿感；与切页重绘叠加时被感知为"切页卡顿"。

**修复建议**：`Snapshot` 内对 COM 探测加 2~3s 缓存；或把设备在线探测整体移到后台线程（`Task.Run` + `UiAsync.Post` 回填），`Tick` 只读缓存。

### PERF-2 🔴 FCT.ini 缺失时每 15 秒全盘深递归扫描（在 UI 线程上）

**位置**
- `Core/FctIni.cs:100-121` — `AutoFindIni()`：对**所有固定盘**先 `SearchFtsTree(root, 8)`（深度 8 递归），全部失败后再 `SearchShallow(root, 5)`
- `Core/FctIni.cs:235-254` — 未命中只缓存 **15 秒**（`_missUntil = DateTime.UtcNow.AddSeconds(15)`，第 250 行）
- `Core/FctIni.cs:102` — `_autoFound` 静态缓存**只缓存成功**，失败不入缓存

**问题**：成功路径被永久缓存（好），但**失败路径只有 15 秒负缓存**。结合 PERF-1（每秒 `Snapshot`），只要 `fct_ini_path` 配错或测试软件不在常规位置，**UI 线程每 15 秒执行一次全盘深度递归**。

**复现**：把 `config.json` 的 `fct_ini_path` 改成一个不存在的路径 → 启动 Argus → 界面每约 15 秒卡一次；用 Process Monitor 可看到对整盘目录的枚举。

**影响**：当前现场 `C:\FTS\Apps\PEU\Cfg\FCT.ini` 存在（本轮采集已确认），所以**线上暂未触发**；一旦换机台/改路径/测试软件升级挪目录，立刻变成周期性严重卡顿。属"埋着的雷"。

**修复建议**：失败也写长缓存（如 10 分钟），或把全盘自动识别改为后台一次性任务 + 设备状态页「立即刷新」按钮手动触发；绝不可挂在 1s Tick 路径上。

### PERF-3 🟠 历史扫描每 100 个文件就全量重算统计

**位置**：`Core/Engine.cs:300-301`
```csharp
AppState.SetScanProgress(parsed: processed);
RefreshStats();          // ← 在 for(每批100个) 循环内
```
`RefreshStats()`（`Engine.cs:325`）→ `AppState.RefreshStats`（`Core/AppState.cs:43-44`）→ `Refresh`（`:50-79`）一次执行 **6 条聚合查询**，其中 `FetchGlobalStats` 是**无日期条件的整表聚合**（`Db/Database.cs:1840-1866`：4×`COUNT` + 1×`COUNT(DISTINCT ...)`，无 WHERE 日期）。

**对比**：实时入库路径**已正确节流 10 秒**（`Engine.cs:471` → `RefreshStatsThrottled`，`:329-336`）。历史扫描这条路径**漏了节流**，属历史遗留不一致。

**量级估算**：现场"37000 文件"≈ `ceil(37000/100)=370` 批 → **370 次 `FetchGlobalStats` 全表 COUNT** + 370×5 次窗口函数查询 ≈ **2200 次 SQL**，其中 370 次扫全表。

**复现**：`skip_historical_scan=false`（现场实测正是 false）启动 → 观察 `[历史扫描]` 期间的 CPU 与库耗时。

**影响**：启动扫描阶段明显变慢；且拉长了写锁竞争窗口，间接放大 ALGO-2（入库失败丢弃）的发生概率。

**修复建议**：循环内改调 `RefreshStatsThrottled()`（或按批数节流，如每 20 批一次），扫描收尾 `FinishHistoricalScan` 再刷终值。

**⚠️ 顺带纠正（见 DOC-1）**：`Engine.cs:327-328` 的注释声称 `RefreshStats` "每条实时记录都全盘枚举 XML"——**这是错的**。`AppState.RefreshStats(db, stationId, resultsRoot)` 第 43-44 行**直接丢弃 `resultsRoot` 参数**，只做库内查询，**不触碰磁盘**。所以本条是"370 次全表 SQL"，不是"370 次全盘扫描"。**不要按错误注释去优化错的方向。**

## 3. 算法与正确性问题（Algorithm / Correctness）

### ALGO-1 🔴 日期口径三套并存 —— 这是"和公司平台对不上"的结构性根因

**位置与证据链**

| 口径 | 实现位置 | 用的时间基准 |
|---|---|---|
| **今日 KPI / 看板** | `Db/Database.cs:1932` — `WHERE test_date = @d` | **目录名日期**（8 位 `\d{8}`，来自 `Parsing/IResultParser.cs:73` + `ParserConfig.cs:14` 的 `(?<date>\d{8})`） |
| **归因 / 透视** | `Database.cs:1547/1570/1594` | **`batch_ts_date`**（时间戳派生，虚拟列见 `:352`） |
| **漂移 / CPK / 分析** | `AnalysisEngine.cs:177-180`、`Database.cs:1657-1661` | **`test_measurements.ts`**（测量时间戳） |

**问题**：同一个"今天"，三处模块用三种基准。`test_date` 是**文件所在的目录名**；`batch_timestamp` 是**文件内/文件名的时间戳**（`Parsing/DefaultResultParser.cs:105-112`，无时间戳时回落目录日 `T00:00:00`）。

**触发条件/复现步骤**
1. 文件放在 `.../20260906/` 目录，但其文件名/内容时间戳为 `2026-09-07 00:30`
2. 触发场景：**跨零点写入**（夜班 23:59 开始、00:01 落盘）、机台时钟与目录归属不一致、人工把文件补放进非当日目录、补扫历史

**影响**：该板被计入 **6 日**而非 7 日。KPI 按目录日，公司平台按 log 时间戳 → 双方今日数字系统性错位。**这正好解释了为什么 v3.36.3→v3.36.8 连续 5 个版本改口径仍对不上**：那几版都在调"SN 去重/复测/Online-Offline"这些**同一天内的聚合规则**，而**根本的日期归属基准没动**。

**修复建议**：先与公司平台确认基准，然后**全局统一到单一基准**。若贴公司口径 → `SnLatestCte` 的 `test_date = @d` 改为 `batch_ts_date = @d`，并对无时间戳记录显式回落 `test_date`；`AppState.cs:53` 的 `DateTime.Now.ToString("yyyyMMdd")` 同步改为对应格式。**绝不可两套混用。**

> **说明**：`SnLatestCte` 内部的聚合规则本身是**自洽的**（见 §5），问题只在"日期基准"这一层。

### ALGO-2 🔴 实时入库异常不重试、不入队 → 永久漏采 → 良率错算

**位置**：`Core/Engine.cs:462-464`
```csharp
try { outcome = _db.UpsertTestRecord(rec); }
catch (Exception ex) { Logger.Error($"[错误] 入库失败: {path} | {ex.Message}"); return; }   // ← 无重试、无入队
```

**问题**：半成品/文件占用走的是"重试队列"（`Engine.cs:407-438`、`EnqueueRetry` `:574-581`，含去重+落盘+停机恢复）。但**入库异常这条路径既不入内存队列、也不落 `retry_queue.json`、普通稳态下也不会被下次历史扫描兜住** → 该 XML 在本进程生命周期内**不再被处理**。

**触发条件/复现**
- 并发写导致 SQLite 写锁超时（`busy_timeout=5000`，`Database.cs:48`）。并发写来源明确存在：
  - 启动时的历史扫描 `BatchUpsert` 单事务（`Engine.cs:289`）
  - `DbMaintenance` 的 Purge / VACUUM（`Db/DbMaintenance.cs`）
  - `DeviceSampleRecorder` 每 300s 写库（`Intelligence/DeviceSampleRecorder.cs:123`）
  - TDMS 特征写入
- 任一处持锁 >5s 即抛 `SQLITE_BUSY` → 被 catch 吞掉丢弃

**影响**：**漏计入库 = 良率错算**。漏 FAIL → 良率偏高（危险，掩盖不良）；漏 PASS → 良率偏低。且**只留一行 ERROR 日志**，现场不会发现。

**修复建议**：入库异常同样入重试队列（复用 `EnqueueRetry`），或对该 `rec` 做有限次重试；并考虑把 `busy_timeout` 提高 / 让维护 VACUUM 避开采集高峰。

### ALGO-3 🟡 漂移"今日窗口"与基线窗口重叠约 21 小时（与注释矛盾）

**位置**：`Intelligence/AnalysisEngine.cs:177-180`

### ALGO-4 🟡 Welford `m2` 未 clamp，理论可产生 NaN

**位置**：`Intelligence/StreamingStats.cs:21` — `Sigma => N < 2 ? 0 : Math.Sqrt(_m2 / (N - 1));`

**问题**：浮点累计误差下 `_m2` 可能为极小负数 → `Sqrt(负数) = NaN`。下游 `Math.Max(NaN, floor)` 在 .NET 返回 NaN，所有比较为 false → **该测项静默不报警**（不报错但也不工作）。

**兜底现状**：写库时 SQLite 把 NaN 存成 NULL，`DeviationScorer.SigmaFloor=1e-6`（`:29-30`）能兜住读回路径。属"有护栏但护栏不是本处"。

**修复建议**：`N < 2 || _m2 <= 0 ? 0 : Math.Sqrt(_m2 / (N - 1))`。
